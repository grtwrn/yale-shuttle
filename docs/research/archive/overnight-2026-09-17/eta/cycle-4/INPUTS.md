# Rider decision audit: inputs and next bounded slice

This is a completed input-feasibility check, not a ranking experiment or app proposal. `input_inventory.py` reads saved data only; `input-inventory.json` records hashes and counts.

The existing raw archive contains12,654 frames and36,516 Red bus observations from four distinct bus names. **It contains no other routes.** It can support a Red-versus-walking diagnostic, not an all-route ranking claim. The five saved warm component snapshots each have only one focal vehicle's full estimator entry. Existing selected traces contain just targets11/48/4 for the focal vehicles. Reusing either as a complete warmed fleet would manufacture missing alternatives.

Current code already has meaningful walking-savings filtering (`walk.savesWalking`), commute-based preference among overlapping/unknown destination windows,90-second clear-arrival separation,30-second persistence before rank changes (`tripRanking`), and third-route visibility memory (`planner.topVisibleOptions`). Pickup availability and destination timing differ: `journeyArrival` must match the catchable boarding occurrence to a later destination occurrence. `TransitMap` live recompute uses that destination distribution after plan generation. Calling `planTrip` alone does not reproduce the card's final live time or ranking. Do not rediscover these policies as missing or tune their thresholds without observed failure evidence.

Record route/bus/board/alight identity, direct and total walk, planned ride, pickup median/floor/range, destination distribution/window, total time, rank/pending state and eligibility reason. Replay exact shell recompute semantics or validate against a bounded actual-shell fixture before calling this UI behavior.
4. Count switches around real rest/first-movement/confirmation transitions; separate changed identity/availability from uncertainty-driven rank changes. 5. Reuse existing connected outcomes only when exact bus/board/alight/occurrence match. Alternate pickup/alight choices require their own connected chains; retain missing chains rather than assigning the focal source's truth to a different chosen trip. The walk baseline is a model, not observed walking time. A selected diagnostic can localize problems but cannot establish general improvement.

For later cross-route ranking, inventory existing authorized watcher/server recordings that actually include those routes and preserve original receipt provenance.
