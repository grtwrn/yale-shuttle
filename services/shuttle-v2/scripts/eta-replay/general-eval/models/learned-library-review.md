The executable library challenger uses scikit-learn 1.8.0's `HistGradientBoostingRegressor` with quantile loss. It can learn interactions between elapsed time, route/stop identity and causal departure history, accepts sample weights, and handles missing and categorical features. The installed Python 3.13.5 environment passed an actual fit/predict smoke test on 2026-09-08. NumPy 2.2.4, SciPy 1.17.0 and joblib 1.5.3 are pinned alongside it in `learned-requirements.txt`. No service dependencies or production files are changed. [Versioned primary API reference](https://scikit-learn.org/1.8/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html).

Development uses September 3 for training, September 4 for model selection, and September 8 for the previously examined regression case. September 5–7 outcomes remain reserved until the feature list and model configuration are frozen. The primary current-stand population is pinned stopped visits. Passes, unpinned visits, unresolved targets and labels unavailable before the fit cutoff remain explicit coverage exclusions; unresolved visits are never relabeled as zero-duration stops. Each training or scored visit has equal total weight, divided among its 30-second observations, and reports include route and long-hold summaries. The selected settings are frozen before refitting on September 3–4 and scoring reserved days.

The strongest complete external engine identified is **OneBusAway/trip-updates**, the current TransitClock fork. Its core performs spatial/temporal matching and prediction, and its API exports GTFS-RT TripUpdates. The repository provides full CSV replay and lighter pipeline tests using an in-memory HSQL database, so PostgreSQL and a deployed public API are not necessary for a bounded offline experiment. [Primary repository and build instructions](https://github.com/OneBusAway/trip-updates).

This differs from the ordinary OneBusAway delivery backend: its documented GTFS-RT integration consumes TripUpdates and VehiclePositions, and requires TripUpdates to display positions. Supplying our predictions to that backend would measure a serving adapter rather than challenge the prediction algorithm. [OneBusAway real-time configuration](https://developer.onebusaway.org/guides/realtime-configuration-guide).

A faithful TransitClock adapter needs the following artifacts:

| Input | Available in this project | Required adapter rule |
| --- | --- | --- |
| Agency, stops, route geometry | Yes | Preserve stop IDs, repeated occurrences and shape direction. |
| Historical vehicle positions | Yes | Preserve recorded timestamps, route assignments, identity reissues and GPS repeats; do not interpolate future movement. |
| GTFS trips, service calendar, stop times and blocks | No static GTFS found in the project | Acquire the applicable historical schedule or estimate one only from training data, and label the latter as an inferred-schedule experiment. |
| Real-time trip/block assignment | Not in the stored app payload | Let the engine match from available GPS/route data; never assign test trips using later observed stops. |
| Replay clock and prediction capture | Engine has CSV replay and pipeline harnesses | Capture only predictions issued before the scored arrival and audit repeatability. |

The current machine has no `java` or `mvn` on PATH. The engine's setup also involves importing GTFS and configuring its matching and prediction runtime. The adaptation risk is primarily the absent trip schedule, not the transport format. [Primary setup guide](https://github.com/OneBusAway/trip-updates/blob/develop/docs/setup.md).

Yale's official Red route description says three shuttles depart at offsets and loop continuously, with loop duration varying with passengers, weather and traffic. It does not supply an exact stop-by-stop timetable. This supports testing a learned departure phase, but does not justify inventing hard `stop_times` values and treating them as ground truth for an external engine. [Official Red route description](https://your.yale.edu/media/3096/download?inline=).

For this overnight run, prioritize the executable learned challenger and preserve this adapter specification. Do not claim TransitClock was benchmarked or is more accurate for Yale. A later complete-engine comparison is meaningful once a historical GTFS schedule exists, or when the result explicitly evaluates a training-only inferred schedule together with the engine. The upstream repository also documents nondeterminism in its full playback harness; use a deterministic stepping harness or repeated runs before attributing small differences to an algorithm. [Primary integration notes](https://github.com/OneBusAway/trip-updates/blob/develop/CLAUDE.md).

The fitted HistGB challenger can run in Node without a Python production dependency. `learned_export.py` exports the frozen 19 quantile ensembles to JSON, and `learned-evaluator.ts` reproduces numerical splits, categorical bitsets, missing-value branches and leaf sums. The traversal follows the pinned scikit-learn implementation, whose leaf values already include learning-rate shrinkage. [Versioned predictor source](https://github.com/scikit-learn/scikit-learn/blob/1.8.0/sklearn/ensemble/_hist_gradient_boosting/_predictor.pyx). The frozen initial remaining-time candidate has 2,850 trees and 82,650 nodes: 2,835,442 bytes of JSON or 904,471 bytes gzip. A 4,894-row parity fixture uses development feature rows plus explicit missing values, unseen categories and threshold boundary cases; all 92,986 quantile values match Python exactly. Measured Node inference median is 3.95 ms/query, p95 7.27 ms/query, with 66.7 ms JSON load on this shared machine. These are feasibility measurements, not browser latency guarantees or held-out accuracy results. See `portable-parity.json` in the learned artifact directory.
